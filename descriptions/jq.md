# Conway's Game of Life in jq

## What is jq?

jq is a **lightweight, command-line JSON processor**. Its intended role in the Unix toolchain is the JSON equivalent of `sed` or `awk`: you pipe JSON into it, write a filter expression, and get transformed JSON out. The canonical use case is processing API responses in shell scripts:

```bash
curl -s https://api.github.com/repos/SimonWaldherr/GameOfLife | jq '.stargazers_count'
```

jq's computation model is **purely functional and stream-oriented**: there are no variables you can reassign, no loops, no I/O beyond reading stdin and writing stdout. Every jq program is a *filter* — a function from an input JSON value to one or more output JSON values. Recursion, list comprehensions (`[... | ...]`), and higher-order functions (`map`, `reduce`, `recurse`) are the primary building blocks.

It was designed for the kind of data transformation that takes milliseconds and fits in a one-liner. It was not designed to run indefinitely, manage state across invocations, or produce animated terminal output.

## How the Implementation Works

### The Two-File Architecture

The implementation (`cgol.jq`) is a Bash script masquerading as a jq program. It has a shebang line (`#!/usr/bin/env bash`) and is valid Bash, but its entire simulation core is a jq expression embedded as a here-string. The split of responsibilities is sharp:

| Layer | Tool | Responsibility |
|-------|------|---------------|
| Shell | Bash | Grid initialisation, animation loop, terminal control, sleeping |
| Core | jq | Neighbour counting, rule application, rendering — all in one invocation |

### Initialisation

Because jq has no per-element random number generator, the initial grid is generated by a single jq call that mixes column index with the current Unix timestamp to approximate randomness:

```bash
W=50; H=30; D=20   # width, height, density (%)

grid=$(jq -n --argjson w $W --argjson h $H --argjson d $D \
  '[range($h) | [range($w) |
    if ((. * 2654435761 + (now * 999983 | floor)) % 100) < $d
    then 1 else 0 end]]')
```

The expression `(. * 2654435761 + (now * 999983 | floor)) % 100` is a simple hash: it multiplies the column index by a large prime, adds a time-based offset, and takes a modulo. The result is not cryptographically random, but it produces visually varied starting patterns. The generated `$grid` is a JSON 2D array — a JSON array of H arrays, each of W integers (0 or 1).

### The Main Loop

The Bash wrapper hides the cursor, clears the screen, and loops forever:

```bash
tput civis; printf '\033[2J'
trap 'tput cnorm' EXIT

while :; do
    out=$(jq -rn --argjson g "$grid" '...')
    printf '\033[H%s' "${out%%$'\x1e'*}"   # print rendered frame
    grid="${out#*$'\x1e'}"                 # extract next-gen JSON
    sleep 0.08
done
```

Crucially, **one jq invocation per frame** produces both the rendered frame and the next-generation JSON, separated by the ASCII record-separator character `\u001e` (0x1e). This avoids writing a temporary file or running jq twice. The Bash string operations `%%` and `#*` split the output on the separator character.

### Inside the jq Expression

The jq filter passed to each invocation does three things: defines helper functions, computes the next generation, and renders the current state.

#### Toroidal Address Lookup

```jq
def idx($x; $m): ((($x % $m) + $m) % $m);
def at($gr; $i; $j): $gr[idx($i; $gr|length)][idx($j; $gr[0]|length)];
```

`idx` wraps a coordinate into `[0, m)` using the double-modulo trick that handles negative indices correctly. `at` uses `idx` on both axes to implement toroidal (wrap-around) grid access.

#### Neighbour Counting

```jq
def neighbors($gr; $i; $j):
  reduce ((-1,0,1)) as $di (0;
    reduce ((-1,0,1)) as $dj (.;
      if ($di==0 and $dj==0) then . else . + at($gr; $i+$di; $j+$dj) end));
```

jq's `reduce` is the functional equivalent of an accumulator loop. The expression `(-1,0,1)` is a jq *generator* — it produces three values in sequence. The nested `reduce` iterates over all nine `(di, dj)` combinations, skipping `(0,0)`, and accumulates the sum of neighbouring cell values.

This is concise but unusual: most languages would write two nested `for` loops. jq uses functional combinators instead.

#### Rule Application (The `step` Function)

```jq
def step:
  . as $gr | [range($gr|length) as $i |
    [range($gr[0]|length) as $j |
      neighbors($gr; $i; $j) as $n | at($gr; $i; $j) as $a |
      if ($n==3) or ($a==1 and $n==2) then 1 else 0 end]];
```

This is a jq list comprehension: for every row index `$i` and every column index `$j`, compute the neighbour count and current cell state, then apply Conway's rules. The result is a new 2D JSON array of the same dimensions.

The expression `range($gr|length) as $i` is idiomatic jq: `range(n)` is a generator that yields integers 0..n-1, and `as $i` binds each value in turn, behaving like a `for` loop inside the comprehension.

#### Rendering

```jq
def render: map(map(if .==1 then "█" else " " end) | join("")) | join("\n");
```

Each row is mapped from `[1,0,1,…]` to `["█"," ","█",…]` and then joined into a single string. The outer `join("\n")` concatenates all rows. The result is a plain text grid of Unicode block characters, ready for `printf`.

#### Combining Output

```jq
$g | "\(render)\u001e\(step | tojson)"
```

This single expression outputs the rendered frame, the record-separator character, and the next generation serialised as JSON — all as one string. The Bash loop then splits on the separator to extract both parts without any temporary files or second jq invocation.

## Is jq Good, Bad, or Ugly for Game of Life?

### 🔴 Verdict: Semantically Inappropriate — and Technically Impressive

jq is arguably the most misused tool in this repository. Its design assumptions are violated in almost every dimension. The result is a testament to functional programming's expressive power, and to the stubbornness of programmers.

**Why it is bad (semantically inappropriate):**

- **No mutable state.** jq has no variables you can update. The grid must be passed as an argument to each invocation and returned in the output — the Bash shell acts as the state store.
- **No loops.** jq has no `while` or `for`. The animation loop is entirely in Bash; jq only handles a single frame at a time.
- **No terminal I/O.** jq cannot move the cursor, clear the screen, or control the terminal in any way. All of that is done with Bash's `tput` and ANSI escape sequences.
- **No native randomness per element.** jq's `now` returns a single timestamp for the entire expression; there is no `rand()` function that produces a fresh value for each cell. The initialisation hash is a workaround for a fundamental limitation.
- **Designed for one-shot transformation.** A jq program is meant to read some JSON, transform it, and exit. Running it 60 times per second in a loop is a deliberate abuse of the tool's intended lifecycle.

**Why it works anyway:**

- jq's **functional data transformation model** maps cleanly onto cellular automaton logic. A Game of Life step is a pure function from grid to grid — exactly what jq is built for.
- **List comprehensions** and **reduce** are genuinely expressive for grid operations. The neighbour-counting code is concise and readable once you understand jq's generator model.
- The **record-separator trick** (computing render and next-gen in one invocation and splitting the output in Bash) is elegant engineering: it avoids the overhead of two jq processes per frame and keeps the shell script simple.
- jq's **raw output mode** (`-r`) and **string interpolation** (`\(...)`) make text rendering straightforward despite jq being a JSON tool.

**What is actually good:**

The implementation showcases jq's strengths in their natural habitat. The `step` and `neighbors` functions are concise, pure, and easy to verify. If you replaced the Bash driver with a single jq program that read a JSON grid on stdin and wrote the next-generation JSON on stdout, you would have a textbook example of how jq should be used. The misuse is in the animation loop and terminal control — not in the simulation logic itself.

## Typical Use Cases for jq

jq excels when:

- The input is **JSON from an API, file, or pipeline** and you need to extract, reshape, or filter it.
- The transformation is **stateless and one-shot** — take this JSON, produce that JSON.
- You are writing a **shell script** and want to avoid a full programming language just to parse a JSON response.
- The logic can be expressed as a **composition of map, select, reduce, and group_by**.

**Classic jq use cases:**

| Domain | Example |
|--------|---------|
| API scripting | Extracting fields from GitHub, AWS, Kubernetes, or any REST API response |
| CI/CD pipelines | Parsing build artefact manifests, test result JSON, or deployment metadata |
| Log processing | Filtering and reformatting structured JSON logs from applications |
| Data transformation | Converting between JSON schemas, flattening nested structures, reshaping arrays |
| Configuration management | Querying and patching JSON-based config files (e.g., `package.json`, Helm values) |
| Infrastructure as code | Processing Terraform state files, Kubernetes resource manifests |

**What jq is not designed for:**

- Stateful computation that persists across invocations
- Animation or interactive terminal applications
- Large-scale data processing (jq is single-threaded and loads all input into memory)
- Anything requiring random number generation per element
- Simulation of any kind

Game of Life needs state, a loop, terminal control, and randomness — none of which jq provides natively. The fact that the implementation works at all is a tribute to the Bash glue layer and to jq's clean functional core.
